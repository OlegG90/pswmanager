## What and why

Phase 0 of #412 — the first shippable step of the modular architecture. It introduces the one pattern every optional feature follows and routes the existing code through it, **with no change in behaviour**: core-owned routing/policy + in-tree category handlers behind a registry, compiled in. Nothing is loaded at runtime.

## What ended up in each module

### Importer registry (`crates/core/src/file_import.rs`)
The `Importer` trait (`id`, `label`, `extensions`, `detect`, `parse`) and four compiled-in importers, in reading order:

| Importer | `detect` | `parse` |
|---|---|---|
| `Aegis` | JSON with `{header, db, version}` | `aegis::read` — plain vault, or the scrypt + AES-256-GCM encrypted one (keys and vault wiped) |
| `Bitwarden` | JSON with `encrypted: true` or an `items[]` | `bitwarden()` — logins, passkeys, cards, identities, secure notes, SSH keys; the encrypted kind refused with its own why |
| `Cxf` | JSON with an `accounts` key | `cxf::read_header` — v1 check, collections→groups, passkeys, `skipped` reasons |
| `Csv` | anything that is not JSON | `csv()` — RFC 4180, the Chrome/Firefox/KeePass/Bitwarden column variants, TOTP, `KP2A_URL_n` |

The router (`parse`/`parse_with_password`) decodes UTF-8 and strips the BOM once, parses a JSON file **once**, offers it to the importers in the order above, then falls back to CSV — every refusal message and the single-parse wiping are preserved.

### Exporter registry (`crates/core/src/file_export.rs` + `vault/reading.rs`)
The `Exporter` trait (`id`, `label`, `extension`, `export`) and two exporters:

- `Csv` → `csv()`: `name,url,username,password,note,totp`, quoted cells, and `left_out` for passkeys / additional fields / attachments / groups.
- `Cxf` → `cxf::export()` with the database-name default (`PswManager`) and the attachment count for `left_out`.

`Format` stays the serialized enum (`"csv"`/`"cxf"`); `Format::extension` now delegates to the exporter. `vault/reading::export_file` routes through the registry.

### StorePlugin registry (`crates/core/src/remote.rs`)
The `StorePlugin` trait (`id`, `needs_network`, `list`, `create`, `open`, `provider`, `describe`, `name`) and five plugins — `FolderPlugin`, `DropboxPlugin`, `GooglePlugin`, `OneDrivePlugin`, `DocumentPlugin` — each owning its own `list/create/open`, OAuth provider, and display text.

`Location::open/describe/name` and `Cloud::list/create/provider` now route through the plugin for the location's/cloud's id. The `Location`/`Cloud` enums and their serde shape are **untouched**, so existing state files keep reading.

### CategoryFiller registry (`crates/core/src/autofill.rs`)
The `CategoryFiller` trait and `LoginFiller`, the first (and only) filler, owning the login category's database work: `offers` (`logins_for`), `choices` (`entries_for_login`), `candidates` (`login_candidates`), `fills` (`login`), `saves` (`save_login`), `links` (`link_login`).

The `Autofill` router keeps the policy — the `Asker` check (`place`/`caller`), locked answers, wiping, confirmations, the `changed` hook — and delegates only the category's work after that check.

## What is untouched (non-goals respected)

- Passkeys/WebAuthn and TOTP/2FA are not modules and have no off switch.
- Site-icon fetching policy stays in `icons.rs`; no icon packs yet.
- List sorting stays the closed `ListSort`/`ORDERS`.
- Merge/sync decision, history limits, `MasterKeyChanged`, and the KDBX round-trip guarantee are unchanged.

## Security & privacy review

- **What new code can read:** nothing new. Importers read the same parsed JSON/CSV bytes as before; exporters read the same entries; store plugins and the login filler delegate to the code they came from.
- **Cleartext and wiping:** a JSON import is still parsed once and wiped (`cxf::wipe`) after routing; CSV content is still wiped by the caller; exports are still built at full size and wiped on drop. The exporter now collects `EntryRef` handles (a database pointer + id), not entry data, so no new copy of secret bytes is made.
- **What leaves the device:** unchanged — icons stay host-only, cloud traffic is the same, no new network path.
- **Certificate/origin checks:** unchanged — `who_asks`, `place()` and `caller()` still run in the router before any filler.
- **Locked-state answers:** unchanged — `session.read` still errors while locked, before any filler runs.
- **Card filler:** it does not exist yet (Phase 3), so it cannot weaken login/passkey paths.

- Phase 2: store capabilities in settings + docs for adding a store (WebDAV/Nextcloud as the first new one).
